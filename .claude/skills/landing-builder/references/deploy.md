# Деплой: от папки с кодом до работающего сайта на домене

Пошаговый операционный гайд. Архитектурные решения (страна сервера, стек) уже приняты в architecture.md — здесь только исполнение. Веди пользователя по шагам и выполняй сам всё, что можешь выполнить (SSH-команды, конфиги); у пользователя проси только то, что требует его личных действий: оплата, коды подтверждения, вход в личные кабинеты.

## 1. Домен

- **Есть домен** → доступ к DNS-панели, дальше п. 3.
- **Нет домена** → сначала проверь whois очевидных кандидатов (имя-фамилия.ru, бренд.ru и вариации): домен нередко уже зарегистрирован самим владельцем и забыт — смотри регистратора и дату оплаты, спроси пользователя. Если действительно нет — для юрисдикции РФ регистрируй у российского регистратора (Reg.ru, Timeweb, Rucenter). Помоги выбрать имя: короткое, читается со слуха, без дефисов и цифр, .ru для локального бизнеса. Покупает пользователь (его аккаунт! — домен должен принадлежать владельцу бизнеса, не подрядчику и не тебе).

## 2. Сервер

- **Есть сервер** → проверь страну (для РФ — дата-центр в России, это требование 152-ФЗ) и доступ по SSH.
- **Сервер уже обслуживает другие сайты** (частый случай у малого бизнеса — один VPS на всё) → прежде чем что-то ставить, осмотрись: `ls /etc/nginx/sites-enabled/`, занятые порты (`ss -tlnp`), запущенные сервисы. Чужие конфиги не трогай. Проекту — своё: отдельный системный пользователь, свои пути (`/var/www/<проект>`, `/opt/<проект>`, база в `/var/lib/<проект>`), свой nginx-конфиг и systemd-юнит с именем проекта, свободный локальный порт. ufw может быть выключен намеренно — не включай его на чужом сервере без согласования, чтобы не отрезать соседей.
- **Нет сервера** → минимальный VPS (1 CPU / 1 ГБ RAM хватает лендингу с запасом), Ubuntu LTS. Рекомендуемые варианты для юрисдикции РФ: **Beget** (просто, дёшево, SSH доступен сразу) или **Яндекс Клауд** (подходит для РФ, есть отдельный регион для Казахстана; при привязке карты ИП и юрлицам даётся приветственный денежный грант — предложи попробовать). Timeweb не рекомендуй для VPS: у новых серверов часто закрыт файрвол снаружи (порт 22 недоступен) — если пользователь уже взял Timeweb и подключиться не удаётся, пусть откроет в панели порты 22/80/443. При заказе — минимальная конфигурация без допов: дополнительные диски, повышенные IOPS и платные бэкап-опции лендингу не нужны. Заказывает пользователь на свой аккаунт; root-пароль или ключ передаёт тебе для настройки. Первым делом поставь свой SSH-ключ — дальше работай по ключу, а пароль, засветившийся в переписке, пользователь потом сменит (см. п. 10).

Первичная настройка (выполняешь сам по SSH):

```bash
adduser deploy && usermod -aG sudo deploy     # не работать под root
mkdir -p ~deploy/.ssh && cp ~/.ssh/authorized_keys ~deploy/.ssh/
# в /etc/ssh/sshd_config: PasswordAuthentication no, PermitRootLogin no
ufw allow OpenSSH && ufw allow 'Nginx Full' && ufw enable
apt update && apt install -y nginx python3-venv certbot python3-certbot-nginx sqlite3
```

## 3. DNS

В панели регистратора: A-запись `@` → IP сервера, A-запись `www` → тот же IP. Проверять не публичный резолвер, а **все авторитетные NS зоны**: `dig +short NS домен`, затем `dig +short @каждый-NS домен` — секондари синхронизируются не одновременно, и пока хотя бы один NS отдаёт старый IP, выпуск сертификата может провалиться, а неудачные выпуски у Let's Encrypt лимитируются. Certbot запускай только когда все NS отдают новый IP (ожидание удобно повесить фоновым поллингом). Пока DNS едет, сайт можно показать пользователю через временный server-блок nginx по IP на нестандартном порту — удали его после выпуска сертификата.

## 3а. GitHub — до выкладки на сервер

Момент для репозитория — когда локальная версия проверена и утверждена, перед деплоем: раньше бессмысленно (макеты меняются пачками), позже опасно (код в бою без резервной копии). Предложи пользователю сам, не жди вопроса:

- репозиторий **приватный**, на аккаунте владельца;
- `.gitignore` до первого коммита: `.env`, база (`*.db`, `*.sqlite3`), бэкапы, venv, `__pycache__` — секреты и данные клиентов в git не попадают никогда;
- после каждой значимой правки — коммит и пуш; деплой правок = пуш + rsync на сервер + перезапуск сервиса.

## 4. Код на сервере

```
/var/www/site/          ← статика (index.html, policy.html, consent.html, оферта)
/opt/app/               ← бэкенд: main.py, venv, .env, leads.sqlite3
/opt/app/backups/       ← бэкапы базы
```

- `.env` (права 600): `TG_BOT_TOKEN`, `TG_CHAT_ID`, `ADMIN_PASSWORD_HASH`, `CONSENT_VERSION`. Секретов в коде и в git нет.
- База SQLite — вне webroot (`/opt/app/`), недоступна по HTTP.

systemd-сервис `/etc/systemd/system/leads.service`:

```ini
[Unit]
Description=Lead form backend
After=network.target
[Service]
User=deploy
WorkingDirectory=/opt/app
EnvironmentFile=/opt/app/.env
ExecStart=/opt/app/venv/bin/uvicorn main:app --host 127.0.0.1 --port 8100
Restart=always
[Install]
WantedBy=multi-user.target
```

`systemctl enable --now leads` → `systemctl status leads` должен быть active.

## 5. nginx и HTTPS

Конфиг `/etc/nginx/sites-available/site`:

```nginx
server {
    server_name домен www.домен;
    root /var/www/site;
    index index.html;
    location /api/   { proxy_pass http://127.0.0.1:8100; }
    location /admin  { proxy_pass http://127.0.0.1:8100; }
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;
    add_header Strict-Transport-Security "max-age=31536000" always;
}
```

`ln -s` в sites-enabled, `nginx -t`, `systemctl reload nginx`. Затем HTTPS:

```bash
certbot --nginx -d домен -d www.домен
systemctl list-timers | grep certbot   # автопродление включено
```

## 6. Telegram-уведомления

1. Пользователь создаёт бота: в Telegram → @BotFather → `/newbot` → имя → получает **токен**. Токен присылает тебе, ты кладёшь в `.env`.
2. Пользователь пишет своему боту любое сообщение (иначе бот не может писать первым). Дай **прямую ссылку** `t.me/<username_бота>` (username возьми из `getMe`) — «Старт», отправленный похожему по имени боту, для пользователя выглядит точно так же, а getUpdates остаётся пустым. Это случается регулярно.
3. Получи chat_id: `curl https://api.telegram.org/bot<TOKEN>/getUpdates` → `message.chat.id` → в `.env`. Если getUpdates пуст, хотя пользователь «уже написал»: проверь `getWebhookInfo` (установленный webhook перехватывает updates) и подожди сообщение фоновым поллингом, а не расспросами.
4. Бэкенд шлёт при новой заявке: `Новая заявка №{id} — {домен}/admin` — **БЕЗ имени и телефона** (для РФ это ещё и защита от трансграничной передачи ПД).
5. Тест: `curl -X POST .../sendMessage` — сообщение дошло.

## 7. Метрика и cookie-баннер

- Пользователь заводит счётчик в Яндекс Метрике (его аккаунт), даёт номер счётчика.
- Код счётчика — на все страницы; цель «Отправка формы» — на событие успешной отправки (`ym(ID,'reachGoal','lead')` в обработчике успеха).
- Cookie-баннер уже в сборке — проверь, что он виден при первом заходе и ссылается на политику.
- Через сутки после запуска проверь в Метрике, что визиты и цель считаются.

## 8. Бэкапы

```bash
crontab -e:  0 4 * * * sqlite3 /opt/app/leads.sqlite3 ".backup /opt/app/backups/leads-$(date +\%F).sqlite3" && ls -t /opt/app/backups/*.sqlite3 | tail -n +31 | xargs rm -f
```

Бэкап остаётся на том же сервере (юрисдикция РФ — данные не уезжают). Проверь, что первый бэкап создался.

## 9. Сквозной тест — обязателен, без него запуск не считается

Прогони РЕАЛЬНЫЙ сценарий с телефона (не с localhost):

1. Открыть сайт по домену с мобильного → HTTPS работает, http редиректит на https.
2. Отправить форму БЕЗ чекбокса согласия → не уходит, ошибка с объяснением.
3. Отправить тестовую заявку с чекбоксом → успех с обещанием.
4. В Telegram пришло «Новая заявка №N» без ПД.
5. В админке заявка видна целиком: имя, телефон, комментарий, отметка рассылки, версия согласия, IP, время.
6. Сменить статус заявки, выгрузить CSV, удалить тестовую запись.
7. Открыть политику, согласие (и оферту, если есть) — все ссылки работают.
8. Cookie-баннер показался, «Понятно» запомнилось.
9. Метрика: визит виден, цель по тестовой заявке сработала.

## 10. Передача владельцу

Владелец должен остаться хозяином всего. Передай и проверь:

- **Доступы:** домен (аккаунт регистратора — его), сервер (пароль/ключ), админка (логин-пароль), бот (токен), Метрика (его аккаунт).
- **Инструкция на одну страницу:** как открыть админку, как менять статусы, как выгрузить CSV, что делать при запросе «удалите мои данные» (найти → удалить → ответить), куда смотреть, если заявки перестали приходить (`systemctl status leads`).
- **Напоминание про госорган:** для РФ — уведомление Роскомнадзора (pd.rkn.gov.ru) подаёт только сам оператор, ДО начала сбора заявок.
- **Смена засвеченных паролей:** всё, что передавалось в переписке (root-пароль сервера и т. п.), пользователь меняет после перехода на ключи — напомни явно, сам он не вспомнит.
- Тестовые заявки из базы удалены.
